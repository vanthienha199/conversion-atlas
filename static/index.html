Using the Conversion Console

A local, read-only console for the Verilog to TL-Verilog conversion flow. It watches a conversion's history/ directory and the agent's transcript, and shows what the AI did at every step, live as it works. No setup beyond Python, and it never changes your files. The Explore / Guide toggle in the top bar switches between the working view and this guide.

Launch it

Run the server in your conversion repo, or point it at a path, then open the printed URL.

# auto-detect conversion dirs in the current repo
python3 server.py

# or point it at a specific path (one module or a whole tree)
python3 server.py path/to/serv/tlv

Open http://127.0.0.1:8765. Python 3.8+, no npm, no build step.

1. Pick a module

Use the dropdown in the top bar. It lists every conversion the server found, with each module's step count and flavor (Gen 2 agentic, or Gen 1 prompt-driven). The module header then shows the path, the module name, the flavor, the checkpoint and task counts, and whether the conversion is complete (only when it actually finished) or in progress with how many checkpoints passed FEV.

2. Walk the history (left panel)

The left panel is the History: every checkpoint the flow recorded, grouped into lanes by task. Click a step, or use the up and down arrow keys, to move through the conversion.

  • Each step shows its real FEV result: a green check if it passed, a red cross with the reason if it failed (for example SandPiper failed or Incremental FEV failed).
  • Steps that ran no FEV are dimmed with a tag: no change for a task the agent completed without touching the code, and baseline for the prepared starting point. They keep the task flow complete without implying work happened.
  • The difficulty profile above the timeline draws one bar per task: bar height is the checkpoint count, and the color gets warmer the more FEV failed there. Tall and warm is a task the agent fought, which is where the instructions likely need work. Click a bar to jump to it.

3. The task header

Above the tabs is a collapsible Task header. It always shows the name of the task being worked on, so you keep it in view on any tab, and it expands to the full task description, the instructions the agent was following at that step.

4. Read each step (the tabs)

  • Diff: a side-by-side diff of each changed file versus the previous step, with unchanged regions collapsed and only the changed words highlighted. The file list marks what changed (M/A/D with line counts). Each file has prev and next buttons so you can step that one file through the checkpoints with it staying in view, handy for watching wip.tlv evolve from Verilog to TL-Verilog. A vs original Verilog button compares the current TLV against the starting point.
  • Files: open any file saved at this checkpoint, or in the working directory.
  • Status: the raw status.json for the step.
  • FEV: the actual fev.sh output the agent saw at this step, pulled from the transcript and lined up with the checkpoint. On a failed step the EQY failure analysis is highlighted, so you can see why it failed without opening logs.
  • Tracker: what the agent recorded about this step. fev.sh snapshots the checkpoint before the agent writes its notes, so a step's notes land in the next checkpoint; the console shows the diff of this step versus the next, rendered as markdown with added blocks in green, plus the full after- and before-trackers, collapsible.
  • Sessions: the agent's full conversation when a transcript is available, with a cost estimate at the top (see the note below).

5. Watch a conversion live

When a conversion is running on this machine, the console follows it in real time over a live connection to the history/ directory. The Live dot turns green, new checkpoints appear and flash as they land, and a strip at the top says whether the agent is working or possibly stuck (retrying FEV without landing a new checkpoint). Use the Follow toggle to keep the newest step in view, or turn it off to inspect history without being pulled forward.

How the conversion flow works

In the Gen 2 flow the agent does the whole conversion from one prompt: it edits wip.tlv, runs ./scripts/fev.sh to verify the change, debugs, and repeats, advancing through a fixed list of refactoring tasks with get_task.py next.

fev.sh runs SandPiper (TL-Verilog to Verilog) and formal equivalence verification with EQY to prove the new code behaves identically, first incrementally versus the last good version, then a full check versus the original Verilog. It records a checkpoint into history/NNN/ after the status is written, so a passing step reads honestly and each failed attempt gets its own checkpoint you can diff.

Every task gets a history entry, even ones that change no code: the prepared baseline is recorded by prep.sh, and get_task.py records a snapshot for a no-op task when nothing else did. That is what fills the dimmed steps in the timeline. The console reads this directory and the transcript only; it never changes your files.

A note on cost

The dollar figure on the Sessions tab is an estimate computed from the transcript's token usage at public list prices. The real billed amount is on your AI provider's cost dashboard and can differ. Model choice dominates cost: a heavier model can run several times the cost of a lighter one for the same conversion.
